<section>
  # 可行方案的初筛

  下面从几个角度尝试迅速缩小可选的解决方案数量。
  <section>
    ## 一些约束

    考虑项目内容、当前的宏观经济与行业状况，以下约束并不难提出：
    <section>
      ### 作者的角度

      - 低开销：保持本项目能被完整访问所需的总费用应尽量低，尤其是周期性费用。
      - 期望获得更多认可：例如增加点击量、GitHub Stars。
      - 提升计算机/软工相关能力，积累项目经验（包括练习使用未曾使用的依赖）。
      - 如选中相对小众的软件生态，本项目将作为一个可行实现。

      最后 2 点常用于决定局部最优解已足够，而不需将所有可能的方案都考虑完全。
    </section>
    <section>
      ### 读者的角度

      - 低技术门槛：读者不一定具有足够的计算机背景，尤其是正准备学习计算机科学的读者。不但需要使得他们轻易访问本项目的全部内容，而且获取到的是最新版本。
      - 低经济门槛与高性能：在廉价消费电子设备上能够流畅阅读本项目的完整内容。必须充分考虑经济条件不佳或被家长禁止购买配置较高的电子设备的读者。
    </section>
  </section>
  <section>
    ## 易于发现与传播

    一个人若要尝试了解一个话题，往往离不开搜索引擎。虽然现在有了 AI，但 AI 也需要通过 Web 搜索来提升回答质量。因此，为了令本项目易于被发现，本项目需要能被通用搜索引擎（Google、Bing、百度、Yandex 等）搜索到。

    不合适的例子：
    - 公网不可访问的离线文件（难以被主流通用搜索引擎检索）。

    为了使（最新版本的）本项目易于传播，应当使得分享本项目时不需发送其完整内容，而是仅发送标识符。而 Web 常用的标识符是 URL（可以是一个或多个）。
  </section>
  <section>
    ## 能在浏览器中查看

    不同的消费电子设备（如 PC、手机、平板）不一定预装了相同的软件。但几乎可以肯定的是，这些设备预装了 Web 浏览器，否则不具有计算机背景的用户不便直接浏览网页。因而，如果一个方案交付的产物无法在 Web 浏览器中查看，比如需要运行设备上尚不存在的可执行文件（应用程序），那么这个方案就可以直接否决。

    不合适的例子：
    - 微信、支付宝、抖音等的小程序；Telegram、Slack、Teams、LINE 等的 App / Mini App。
    - 单独的应用（需要下载和/或安装并运行的客户端）。

    一个符合 HTML 标准的浏览器（用户代理）在访问指定的 URL 时，只被要求直接加载具有下列 MIME 类型的实体<Cite references={R} cite_items={[ { condition: 'HTML Living Standard', label: 'section', locator: '7.4.6' } ]}/>：
    - HTML
    - 不被<u>显式支持</u>（被配置为使用外部应用程序打开或其它专用处理规则处理）的 XML
    - JavaScript
    - 不被显式支持的 JSON
    - text/css
    - text/plain
    - text/vtt
    - multipart/x-mixed-replace
    - 图像、视频或音频
    - application/pdf
    - text/pdf

    接下来可以按 MIME 类型进一步排除：
    - 首先排除 PDF（application/pdf、text/pdf）。因为 PDF 是固定版式，无法适应不同的显示区域（根据不同的宽高比、分辨率等自动重排），也不便于切换样式（例如切换黑暗主题而不引起图像失真）。这会给持有不同设备的用户的流畅阅读带来麻烦。
    - 其次排除视频或音频，以及网络视频文本轨道（WebVTT，text/vtt）。因为本项目以文本为主（同时符合本项目主张的 “优先文字材料而非视频” 的思想）。
      - 图像特别是SVG（即 image/svg+xml）可以在本项目中采用，但本项目以文本为主，而不是一张或多张图像。
    - 然后排除纯文本（text/plain）、层叠样式表（text/css）、JavaScript 脚本（text/javascript）、不被显式支持的 JSON，因为浏览器会直接显示原始内容<Cite references={R} cite_items={[ { condition: 'HTML Living Standard', label: 'section', locator: '7.4.6, 7.5.4' } ]}/>（虽然主流浏览器往往展示 JSON 的树结构，即具有 JSON 的显式支持），无法显示本项目所需的富文本。
    - 排除不被显式支持的 XML：
      - 若其采用了 HTML 命名空间，则该 XML 文档成为 XHTML（application/xhtml+xml）<Cite references={R} cite_items={[ { condition: 'HTML Living Standard', label: 'section', locator: '1.7' } ]}/>：XHTML 句法已不再维护<Cite references={R} cite_items={[ { condition: 'HTML Living Standard', label: 'section', locator: '14' } ]}/>，同时亦无任何规范定义 XML 解析器如何将字节流或字符流映射为 DOM 对象<Cite references={R} cite_items={[ { condition: 'HTML Living Standard', label: 'section', locator: '14.2' } ]}/>。目前没有找到其它合适的理由继续使用它。
      - 若其不采用 HTML 命名空间，则浏览器往往会直接显示 XML 的内容（以树结构呈现），无法显示本项目所需的富文本；即便得以关联 CSS 或 XSLT（主流浏览器已弃用<Cite references={R} cite_items={[ { condition: m => m.title === 'Should we remove XSLT from the web platform?' }, { condition: m => m.title === 'XSLTProcessor' && m['container-title'] === 'MDN Web Docs' } ]}/>或移除支持<Cite references={R} cite_items={[ { condition: m => m.title === 'Removing XSLT for a more secure browser' }, { condition: m => m.title === 'Deprecate and remove XSLT' && m['container-title'] === 'Chrome Platform Status' } ]}/>）样式表，自定义标签缺乏 HTML 原生语义与元信息，不利于搜索引擎优化（SEO），进而不利于增加本项目的曝光。
    - 排除 multipart/x-mixed-replace：
      - 该 MIME 类型主要用于 MJPEG 实时视频流的更新（逐帧推送 JPEG），早期还用于 HTML 或纯文本片段的持续更新（现代浏览器已不支持）。
      - HTML 标准的加载算法要求加载该类型时递归调用同一加载算法<Cite references={R} cite_items={[ { condition: 'HTML Living Standard', label: 'section', locator: '7.5.5' } ]}/>，故而本项目的交付物不能直接使用此类型，必须具有上述其它 MIME 类型。

    于是候选项只剩下 HTML，其与 CSS、JavaScript 在 Web 生态中往往同时使用，但这时 CSS 和 JavaScript 文件由 HTML 通过`<link>` `<style>` `<script>`等元素链接作为子资源，而不在访问 URL 时直接向用户展示。
  </section>
  <section>
    ## 按项目内容渲染完毕的时间筛选方案

    可以完备地将候选解决方案按照本项目的内容渲染的时间分为下列类别：
    - 在用户访问前渲染完毕。典例：静态站点生成（SSG）。
    - 在用户访问时开始渲染：
      - 在处理请求的过程中（同步或异步按需）渲染。典例：服务端渲染（SSR）及其变体，例如 ESR（边缘渲染）、ISR（增量静态再生成）。
      - 在响应发回用户后渲染。典例：客户端渲染（CSR），包括 SPA（单页应用）等。

    显然，内容在用户访问前渲染完毕，相比在响应请求过程中渲染（SSR 等）可省去服务端的动态计算资源与作者需支付的相关费用，相比在响应发回后渲染（CSR）可降低用户设备流畅浏览项目内容的资源消耗，还更利于通用搜索引擎直接抓取内容。因此，本项目首选静态站点生成（SSG）方法。确有需要时，再引入动态内容。
  </section>
</section>
<section>
  # 非软工方法 v 软工方法

  下面论证引入软件工程方法的必要性。
  <section>
    ## 呈现与内容分离

    原则上，修改视觉呈现的方式时，不应导致呈现内容的（意外）变动；修改呈现内容时，也不应引起呈现方式的（意外）变动。

    考虑本项目的已有与计划中的内容，本项目提及的课程、教科书与参考资料属于典型的多对多关系（$M:N$），应当建模并交由计算机处理，而不仅仅以纯文本的形式书写。这将极大减轻维护负担。此外，当需要对视觉呈现的方法/样式进行一定程度的定制时，不能忽略选定的静态站框架尚未提供，需要编程实现的可能性。

    至此，引入软工方法的理由已经较为充分。
  </section>
  当然，还有更多理由能够说明引入软工方法相比不引入是更佳的方案。
  <section>
    ## 可能引入交互功能

    目前不排除添加交互功能。譬如：
    - 按所选专业/方向展示可以拖动、放大、缩小的课程先修关系图。
    - 部分内容的折叠与展开。
    - 粗粒度与细粒度的样式切换。举例：全站主题、字体、代码高亮的风格。

    一旦选定的静态站框架未实现所需的交互特性，就需要自行编程实现。
  </section>
  <section>
    ## 内容导航与全文搜索的便利

    主流静态站框架常常集成了内容导航与全文搜索机制，例如侧边栏、内建全文搜索框。然而，这些已有功能有时并不足够。举例而言，各框架通常仅实现了倒排索引，于是特殊符号、正则式搜索等搜索方法不受支持。这时往往需要亲自实现缺失的功能。
  </section>
  <section>
    ## 对 Agent 的约束

    近年来，AI 的编程能力进步很快，且 agent 迎来了多次重大进展。为了利用 agent 加快项目进度，必须引入确定性方法来约束 agent 的行为，避免 AI 幻觉破坏已有内容，更要力求这些破坏被及时发现。而编程/软件工程方法，包括但不限于静态类型检查、数据格式/schema 校验、自动化测试等（而不仅仅是在 Markdown 文档中编写 skill），有助于构建这样的约束。
  </section>
</section>
<section>
  # 贡献门槛的考虑

  在大多数场景中，我不认为引入软工方法会带来过高的贡献门槛，因为计算机技能正被越来越多非计算机岗位列为硬性要求。当下的竞争之激烈大家已有目共睹，应当推定已有众多不具有计算机背景的人员正在自学计算机知识并练习相应的技能，从 Git、Markdown 及其变体到基础编程、Web 开发等。AI 亦能明显降低阅读他人代码的成本。另外，如提交 PR 确实感到困难，至少可以直接使用自然语言编写并提交 Issue。
</section>
